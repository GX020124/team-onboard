# Updating Knowledge from Review Feedback

When the user asks only to revise the current output, complete that revision. Persist findings under this guide when the user requests learning, recording, or updating project knowledge, and also read the [knowledge guide](knowledge.md).

## Identify What the Feedback Addresses

Compare the submitted version, specific review comments, and final accepted version. State which evidence is available when any part is missing. A direct comment can establish a requirement for this task; a final version alone does not explain every change.

Classify the feedback before deciding what belongs in reusable knowledge:

| Type | Treatment |
| --- | --- |
| Functionality, business rules, or correctness | Update facts or implementation constraints within the relevant business scope, rather than turning them into cosmetic preferences |
| Project or module conventions | Record the explicit requirement and scope, with relevant examples |
| Document or reporting preferences | Scope to the deliverable type, readers, and occasion |
| One-off arrangements | Apply to this task; retain as scoped facts only if useful later |
| Unexplained changes | Record as unconfirmed observations without inventing reviewer intent |

Establish how each comment relates to the resulting change. Exclude unrelated refactoring, formatting, and automatic fixes from preference conclusions.

## Update Relevant Entries

1. Find existing facts, rules, and sources. Determine whether feedback adds evidence, narrows scope, creates an exception, or replaces a conclusion.
2. Apply clear requirements within their stated scope. Do not automatically promote a single comment to a project-wide rule, or use silence or one merged change to justify broader scope.
3. Update a clearly superseded entry and briefly explain why, marking the old entry obsolete when retained. Keep differences across modules or occasions separate. Preserve both references and an unconfirmed status when a consequential conflict remains unresolved.
4. Update only affected topics and the index. Add genuinely new evidence to existing feedback entries instead of appending duplicate conclusions.

An explicit request such as "use this approach for this kind of document from now on" can establish guidance for that document type. Surface conflicts with current team requirements before deciding how to apply it.

## Check the Result

Check whether the revision addresses the review, whether saved guidance represents the feedback without expanding its scope, and whether evidence can be located. Without another review, report completed revisions and checks rather than claiming approval.

To evaluate the skill, use historical tasks held out from learning or new tasks. Check behavior and project checks, document structure, and reporting priorities separately. Observe whether convention-related rework decreases, and check conflicting sources, loading across sessions, and project isolation. Repeating learned examples is not evidence of generalization.
