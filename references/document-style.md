# Learning and Applying Document Style

## Choose Comparable Sources

Identify the document's purpose, readers, and delivery format, such as a feature design, technical proposal, architecture decision, or operating guide. Choose current examples with a matching purpose and similar readers. Use explicitly designated examples as references for this task.

Read the actual content and relevant layout, and verify which examples were accepted. A filename, summary, or failed read is not evidence of having learned a document's content or formatting. Use existing capabilities for formats such as Word and PDF, and state reading limitations.

## Extract the Style

- Section and narrative order: how actual examples arrange context, goals, resulting behavior, proposals, boundaries, verification, or rollout.
- Level of detail: what needs explanation, what needs only a conclusion, and how much business or technical context readers require.
- Reasoning: how documents explain tradeoffs, use examples and data, present diagrams, and record open questions.
- Expression and format: terminology, tone, heading levels, lists, tables, captions, and meaningful template conventions.

Keep conventions for different document types separate. When asked to learn or save them, follow the [knowledge guide](knowledge.md) and write findings and example references to the target project's document topic, defaulting to `.team-context/document-style.md`.

## Produce the Current Document

1. Establish facts from the current requirement, implementation, and verified sources, then read the rules and examples for the document type.
2. Follow applicable structure and wording, with length proportional to the task's complexity. Do not inherit an example's specific proposal, figures, dates, or progress claims.
3. Distinguish implemented behavior, plans, and open decisions. Omit irrelevant template sections and identify missing information instead of inventing conclusions to fill them.
4. When editing an existing document, preserve its organization and unrelated content. Use existing document-generation capabilities for requested file formats and inspect the actual rendered result.

When examples are insufficient, produce a suitable draft and identify provisional structural choices. Do not present generic writing practices as learned company conventions.

Before delivery, check factual sources, commitments and boundaries, terminology, and structural consistency. Evidence and internal verification notes can be reported separately; include them in the document only when its purpose or the user requires them.
